## 확정 — 데이터 소스

**Steam 동시접속자.** 대표값은 Counter-Strike 2 (appid 730).

```
GET https://api.steampowered.com/ISteamUserStats/GetNumberOfCurrentPlayers/v1/?appid=730
→ 200  application/json  인증 키 없음  공식 문서 있음
→ {"response":{"player_count":551673,"result":1}}
```

동시접속자 데이터에 쓰는 엔드포인트는 이것 **하나뿐이다.** 게임 이름은 `GAMES`
표에 우리가 적었고 원자료와 잇는 열쇠는 appid 다. 가격 실험의 비공식 Store 경로는
아래 8차 결정에 분리해 기록했으며 이름·장르·동시접속자에는 사용하지 않는다.

### 소재를 Stack Overflow 에서 바꾼 이유

8/26~8/27 에 Stack Overflow 신규 질문 수로 기록 2건(65건·67건)까지 갔다가 바꿨다.
그 코드와 기록은 커밋 `0883883` 에 그대로 있다.

바꾼 이유는 **대중성과 포트폴리오 인상**이다. 과제 요건은 양쪽 다 만족했다.

### 바꾸면서 잃은 것 — 정직하게 남긴다

| 잃은 것 | 내용 |
|---|---|
| **원자료 대조 재현성** | 동시접속자는 순간값이라 심사자가 출처 링크를 눌러도 화면의 기록값과 절대 일치하지 않는다. 40분 사이 572,811 → 551,673 으로 움직였다. Stack Overflow 는 확정값이라 1년 뒤에 열어도 같은 값이 나왔다 |
| **기록 2건** | 8/25·8/26 기록을 버리고 8/27 부터 다시 모은다. 하루 손해 |
| **브라우저 직접 호출** | Stack Exchange 는 CORS `*` 였다. Steam 은 열려 있지 않다 |

대조 재현성 문제는 **화면에 명시해서 다룬다.** 숨기면 카드 1 체크리스트에 걸리고,
드러내면 과제가 원하는 태도가 된다.

### 알고 시작하는 약점

1. **순간값이라 원자료 대조가 안 된다.** 위 표 참조. 화면에 적어서 다룬다.
2. **`LIVE` 라고 쓸 수 없다.** Actions 가 하루 한 번 받으므로 방문자가 보는 값은
   최대 24시간 지난 값이다. `2026-08-27 10:10 KST 측정` 으로 적는다.
3. **과거를 메울 수 없다.** 수집이 하루 빠지면 그날은 영영 빈칸이다.
   `assertMeasurableNow()` 가 되돌려 채우는 것을 막는다.
4. **`KING OF TODAY` 는 만들지 않는다.** 상위 1~4위가 주간 기준으로 고정이라
   (실측) 매일 같은 게임이 나온다. 변하지 않는 값을 크게 띄우지 않는다.

## 설계 불변식 — 코드보다 먼저 정한 것

> **화면에 보이는 값·단위·출처·출처 관측 시각·날짜·조회시각은 언제나 하나의 응답 객체에서
> 나온다. 절대 따로 전달하지 않는다.**

```js
Reading = { value, unit, date, appid, signalId, sourceUrl, sourceLabel, sourceTime, timezone, fetchedAt }
```

`sourceTime`은 원천이 제공한 관측 시각, `fetchedAt`은 우리가 조회한 시각이다.
Steam 동시접속자 API는 원천 관측 시각을 주지 않으므로 `sourceTime: null`로 저장하고
화면에 미제공이라고 밝힌다. HTTP `Date`는 응답 시각일 뿐 관측 시각이 아니어서 대신
쓰지 않는다. 묶어서만 다루면 "값은 새 것인데 시각은 옛 것"이 구조적으로 불가능하다.
`Reading`이 없으면 숫자 자리에 넣을 것도 없다.

```
state ∈ FRESH | STALE | EMPTY
fault ∈ TIMEOUT | AUTH | RATE_LIMIT | OFFLINE | SCHEMA
```

`STALE` 은 마지막 정상값을 보여주되 잰 시각을 **절대 now 로 갱신하지 않는다.**
`EMPTY` 는 숫자 자리에 `—`.

작업 규칙 전체는 [CLAUDE.md](../CLAUDE.md) 에 있다.

### 비율의 분모는 아는 것이어야 한다

3층 줄세우기 패널의 %는 **우리가 잰 게임 안에서의 비중**이다. Steam 전체에서의
비중이 아니다.

전체 동시접속자는 이 엔드포인트가 주지 않는다. 모르는 값을 분모로 쓰면 %는
그럴듯한 모양을 갖추지만 **아무것도 뜻하지 않는다** — 그리고 화면을 보는 사람은
그것을 `Steam 점유율` 로 읽는다. 그래서 분모를 화면에 숫자로 적었다.
위 값들을 손으로 더하면 그 분모가 나온다.

같은 이유로 못 가져온 게임은 **행을 만들지 않는다.** 0 으로 채우면 `아무도 안
한다` 와 `못 쟀다` 가 화면에서 같은 모양이 된다. 진짜 0 명인 게임은 행이 있고
비중이 0 이다 — 이 둘이 구별되는지는 테스트로 고정했다.

### 참고 화면(MSN 날씨)에서 가져온 것과 바꾼 것

배치는 [디자인 참고 사이트 예시](research/디자인%20참고%20사이트%20예시.md) 에 적어 둔
MSN 날씨 구조를 따랐다. **다만 그대로 가져오면 깨지는 것이 셋 있어 바꿨다.**

| 저쪽 | 이쪽 | 왜 바꿨나 |
|---|---|---|
| 나브를 누르면 내용이 갈아끼워진다 | 누르면 그 구획으로 **내려간다** (앵커 + 스크롤스파이) | 브리프가 카드 1·5 의 통과 기준을 `한 화면에 보인다` 로 못박았다. 탭 뒤로 숨기면 그 순간 조건이 깨진다 |
| 날짜 스트립 오른쪽이 **예보**로 채워진다 | 잰 날만 카드가 된다. 미래 칸도 빠진 날 칸도 안 만든다 | 동시접속자는 부르는 순간의 값이라 예보가 없다. 빈 칸을 그리면 "곧 채워질 값" 이 아니라 **아는 척하는 값**이 된다 |
| 설정에서 지역·언어를 고른다 | 고를 수 있는 것은 **대표 게임뿐**. 시간대·재는 시각·단위는 적어 두기만 한다 | 값이 그 시간대의 그 시각에 잰 것이다. 화면에서 시간대를 바꾸면 잰 시각과 보는 시각이 어긋나고, 그 어긋남이 이 정보판이 잡아내려는 거짓말이다 |

그대로 가져온 것은 배치다 — 왼쪽 로고 · 가운데 검색 · 오른쪽 설정, 구획 나브,
오른쪽 아래 맨위로·새로 고침.

**게임을 바꿔도 API 를 더 부르지 않는다.** 재는 게임을 이미 같은 시각에 다 재 뒀고,
고르는 것은 그중 어느 줄을 크게 볼지다. 고른 게임은 `?game=` 으로 주소에 남아
"내가 본 화면" 을 링크로 넘길 수 있다.

**고른 게임에 기록이 없으면 기본값으로 되돌아가지 않는다.** EMPTY 를 준다.
되돌아가면 화면은 CS2 값을 보여주면서 고른 것은 다른 게임인 상태가 되고, 값과
이름이 어긋난다. `?game=999999` 로 확인했다 — 숫자 자리가 `—` 가 되고 나브에서도
없는 구획이 사라진다.

**새로 고침이 하는 일은 기록 파일을 다시 읽는 것**이지 Steam 을 다시 부르는 것이
아니다. 눌러도 대개 같은 값이 온다. `지금 다시 잰다` 로 읽히면 그것이 곧 `LIVE`
표시와 같은 거짓말이라 툴팁에 적어 두었다.

### 장르 — 넣기로 했고, 대신 세 가지를 지킨다

[개선점01](research/개선점01.md) 의 장르 확장을 넣었다. **처음에는 반대했다** —
그때 16개로는 장르가 통계가 아니라 우리 취향 목록이고, `장르 전쟁` 합계는 바로 위
`비율의 분모` 원칙을 어기며, `KING OF GENRE` 는 이미 측정으로 떨어뜨린
`KING OF TODAY` 와 같은 고정판이 되기 때문이다.

넣기로 한 이유가 더 낫다. **대표값 하나(CS2)만 크게 띄우면 FPS 를 안 하는 사람에게
첫 화면이 남의 이야기가 된다.** 보는 사람의 성향을 모르니 들어오는 문이 여러 개여야
한다. 걱정한 둘은 범위를 줄여서가 아니라 아래 셋으로 막았다.

1. **장르마다 그 안에 든 게임을 값과 함께 다 펼친다.** 분류가 우리 것이라
   보는 사람이 동의하지 않을 수 있고, 그러려면 목록이 보여야 한다.
2. **게임 수를 줄마다 적는다.** 처음엔 1개짜리 장르가 다섯이었고, 그때 1위는
   순위가 아니라 그냥 그 게임 하나였다. 그래서 `우리가 넣은 게임 1개` 로 적어
   왕관을 안 씌웠다. 지금은 장르당 10개지만 MOBA 는 5개라 이 표시가 살아 있다.
3. **분모를 화면에 숫자로 적는다.** 장르 합계의 합이 줄세우기 패널의 분모와 같다
   (8/27 기준 `1,532,446 명`). 두 패널이 서로 검산된다.

장르가 크게 나오는 것이 그 장르가 큰 것은 아니라는 사실을 화면에 적었다. 우리가
그 장르에 게임을 많이 넣은 것일 수 있고, **게임을 고른 것도 우리다.**

### 재는 게임을 16 → 36 → 75 개로 늘렸다

장르를 넣고 보니 분포가 슈터 8 · 나머지 1~3 이었다. 1개짜리 장르가 다섯이면 그건
장르가 아니라 그냥 게임 하나다. 두 번에 걸쳐 **장르당 10개**로 맞췄다.

| 장르 | 개수 |
|---|---:|
| 슈터 · 생존·제작 · RPG · 전략 · 오픈월드 · 시뮬레이션 · 퍼즐 | 각 10 |
| **MOBA** | **5** |

#### MOBA 만 열 개를 못 채웠다 — 억지로 채우지 않았다

Steam 에 MOBA 가 이만큼뿐이다. 후보를 전부 실제로 불러 봤다.

| 후보 | 결과 |
|---|---|
| Deadlock (1422450) | **조회 자체가 안 된다** |
| Battlerite (504370) | 14 명 |
| Awesomenauts (204300) | 35 명 |
| Predecessor (1180200) | **0 명** (`result:1` 이라 진짜 0 이다) |

살아 있는 넷(Dota 2 · Eternal Return · SMITE)에 Battlerite·Awesomenauts 를 더해
다섯으로 뒀다. **없는 것을 있는 것처럼 만들지 않는다**는 규칙이 여기에도 걸린다.
화면의 장르 줄에 개수가 그대로 적히므로 보는 사람이 이 사실을 안다.

#### 줄을 누르면 그 장르가 막대로 펼쳐진다

막대 길이는 **그 장르 안 1위 대비**다. 장르마다 규모가 열 배씩 달라서 전체 1위에
맞추면 작은 장르는 전부 실선이 되어 서로 견줄 수가 없다. 대신 기준이 장르마다
달라지므로 **그 사실을 그래프 아래 적었다** — 안 적으면 다른 장르의 막대와 길이를
견주게 되고 그건 틀린 비교다.

**접혀 있을 때도 이름과 값은 글자로 다 보인다.** 펼쳐야만 보이는 정보를 만들지
않는다 — 브리프의 `한 화면에 보인다` 와 같은 이유다. 펼치기는 읽기 편하라고 있는
것이지 숨기라고 있는 것이 아니다.

그래프에서 게임을 누르면 그 게임이 맨 위 대표값 자리로 간다.

#### 늘어난 비용

| | |
|---|---|
| 수집 시간 | 75개 × (요청 ~0.2s + 대기 0.2s) ≈ **30초** |
| 하루 기록 | 75건. 1년이면 27,375건 |
| 호출 제한 | **모른다.** 75회 연속 호출에서 실패는 없었지만 문서화된 제한을 못 찾았다 |

기록 파일이 커지면 화면이 통째로 받는 구조가 언젠가 걸린다. 지금 규모(며칠치)
에서는 문제가 아니지만 **알고 두는 한계**로 적어 둔다.

**appid·이름·연도는 전부 우리가 적은 주장이다.** 이 엔드포인트는 숫자만 주고
이름도 연도도 주지 않아, 잘못 짝지으면 화면이 조용히 거짓말을 한다. 그래서 75개를
두 가지로 확인했다.

1. **공식 엔드포인트로 불러 `result:1` 과 사람 수를 받았다** — appid 가 실존한다
2. **공개 상점 페이지에서 제목과 출시연도를 눈으로 맞췄다** — 짝이 맞는다

두 번째는 **일회성 개발 확인이고 제품 코드에는 없다.** 리뷰 2-1 검사가 `src/` 와
`scripts/` 어디에도 store 주소가 없는지 본다. 제목에 할인 배너가 껴 있는 것들은
(`Save 70% on Cities: Skylines`) 벗겨서 적었다.

**그 확인이 실제로 셋을 잡았다.** 기억으로 적었으면 그대로 화면에 나갔을 것들이다.

| 내가 알던 것 | 실제 |
|---|---|
| `594570` = Total War: THREE KINGDOMS | **WARHAMMER II** 였다 |
| `1049590` = Escape Simulator | **Eternal Return** 이었다. MOBA 라 장르도 바뀌었다 |
| Path of Exile 1·2 | 상점이 `Site Error` — **확인을 못 해 넣지 않았다** |

셋째가 특히 그렇다. 숫자는 잘 오는 appid 였으니 그냥 넣을 수도 있었다. 넣지 않은
이유는 **숫자가 맞아도 이름이 틀리면 그게 이 정보판이 잡아내려는 거짓말**이기
때문이다. 확인 못 한 것은 안 넣는다.

형식 사고는 테스트가 막는다 — appid 중복, 이름 중복, 연도 범위, tier 값, 대표값
게임이 표 안에 있는지.

#### 2026-08-27에는 실제로 두 수집 배치가 들어갔다

예측했던 사고가 발생했다. 8/27 기록은 **09:59의 16개**와 **20:09의 59개**로
갈렸고, 8/28은 10:39에 75개가 들어갔다. 기록은 사실이므로 지우거나 손으로
고치지 않는다. 대신 화면 계산이 서로 다른 배치를 하루 변화로 가장하지 않게 한다.

수집 실행 ID가 과거 Reading에 없으므로 대표 Reading과 **5분 이내**에 잰 행을 같은
배치로 복원한다. 5분은 날짜 사이의 허용 오차가 아니라 75개를 순차 호출한 한 실행의
소속 경계다. `movers`는 양쪽 날짜에서 대표 배치에 속한 행만 견주고 실제 배치 시각과
제외 건수를 표시한다. 따라서 현재 비교는 `09:59 → 10:39`의 16개이며, 20:09에
들어온 59개는 원본에 남지만 변화 순위에서는 빠진다.

`timeBias`는 같은 KST 날짜이고 표본보다 먼저 측정된 대표 배치만 사용한다. 8/27의
`09:59 → 16:30` 16개는 성립하고, 표본보다 늦은 20:09 배치는 제외한다. 최신 날짜와
표본 날짜가 다르면 같은 날 시각 비교를 만들지 않는다.

`scripts/probe-hours.mjs` 는 **아무 때나 돌려도 된다.** 별도 파일이라 날짜별
기록을 건드리지 않는다.

화면이 오늘 여전히 16개를 보여주는 것도 맞다. `withGenres` 가 **기록 파일의 게임
표**를 돌면서 코드 표의 이름표만 얹기 때문이다. 파일은 잰 것을 담고, 코드 표는
분류를 담는다.

장르 값은 **`store.steampowered.com` 을 부르지 않고 우리가 손으로 적었다.** 공식
API 가 장르를 주지 않고, 주는 경로는 문서화돼 있지 않다(CLAUDE.md 5). 이름·연도를
우리가 적어 둔 것과 같은 취급이다.

**장르는 기록 파일이 아니라 코드 표에서 온다.** 기록 파일은 잰 것을 담고, 장르는 잰
것이 아니다. 나중에 분류를 고치면 지난 기록도 새 분류로 보이는데 그게 맞다 —
분류를 바꾼 것이지 그날 잰 값이 바뀐 것이 아니다. 반대로 값과 이어지는
이름·연도는 파일 것을 그대로 둔다(`withGenres`).

### 개선점01 에서 안 가져온 것

| 제안 | 왜 안 가져왔나 |
|---|---|
| `KING OF GENRE` 왕관 | MOBA 후보가 Dota 2 하나뿐이라 내일도 모레도 같다. 변하지 않는 값을 크게 띄우지 않는다 — `KING OF TODAY` 를 뺀 이유와 같다 |

그 문서의 우선순위 5개 중 셋(어제 대비 · 오른/내린 게임 · 장애 상태)은 이미 서
있었다. 작성자가 `공개 주소가 캐시 오류로 로드되지 않았다` 고 적어 둔 대로 화면을
못 본 상태에서 쓴 제안이다.

**가장 잘 짚은 대목은 분모다** — `절대로 Steam 전체 플레이어의 32.8% 라고 하면
안 돼`. 같은 결론에 독립적으로 도달했고, 줄세우기와 장르 양쪽에 그대로 적용했다.

### 표지 그림 — 규칙 5 의 예외를 좁게 연다

순위 목록과 대표값에 Steam 표지 그림을 붙였다.

```
https://cdn.cloudflare.steamstatic.com/steam/apps/<appid>/capsule_231x87.jpg   목록
https://cdn.cloudflare.steamstatic.com/steam/apps/<appid>/header.jpg           대표값
```

**공식 Web API 문서에 없는 경로다.** 관례로 굳어져 있을 뿐이라 규칙 5 에 걸린다.
그래도 여는 이유는 규칙 5 가 막으려는 것이 *값이 검증 불가능한 경로에서 오는 것*
이고 그림은 값이 아니기 때문이다. 조건 셋은 [CLAUDE.md](../CLAUDE.md) 5번에 적었고,
`test/artwork.test.js` 가 이 경로로 `.jpg` 말고 다른 것이 나가지 않는지 본다.

실측 (2026-08-27):

| | |
|---|---|
| 그때 재던 16개 appid | 전부 `200 image/jpeg` |
| `capsule_231x87` | 개당 5~10KB · 16개 합 약 128KB |
| `header.jpg` | 개당 25~115KB · 16개 합 약 750KB |
| `steamcdn-a.akamaihd.net` | 같은 바이트 |
| `shared.cloudflare.steamstatic.com` | 301 |
| 없는 appid(999999) | 실패 → `onError` 경로가 탄다 |

**목록은 자리를 남기고 그림만 사라진다. 대표값은 자리째 접는다.** 다르게 한
이유가 있다 — 16줄 중 하나만 안 왔을 때 그 줄만 밀리면 그게 더 고장 나 보인다.
대표값은 하나뿐이라 어긋날 상대가 없다. 브라우저에서 확인했다: 목록은 그림 1장만
빠지고 줄 높이·글자가 그대로였고(48/49/49), 대표값은 패널이 334→234px 로 접히며
값·날짜·잰 시각이 안 변했다.

**560px 아래에서는 그림을 뺀다.** 68px 을 그림에 주면 이름 칸이 81px 로 줄어
`The Elder Scrolls V: Skyrim` 같은 이름이 잘린다. 그림은 정보를 안 나르고 이름은
나르므로, 무엇을 버릴지는 정해져 있다. 빼고 나니 이름 칸이 159px 로 돌아왔다.

**대표값 그림만 `eager` 다.** 첫 화면에 바로 보이는 것까지 미루면 제일 중요한
것이 제일 늦게 온다. 목록 16장은 `lazy`.

그림의 권리는 각 퍼블리셔에 있다. 우리가 만든 것이 아니라는 사실과 값이 여기서
오지 않는다는 사실을 순위 패널 아래에 적었다.

**요청이 1개에서 늘었다.** 지금까지 이 화면은 `records.json` 하나만 불렀다.
데이터는 여전히 그 파일 하나뿐이지만("API 를 더 붙이지 않았다" 는 그대로 참이다),
보는 시점에 남의 호스트에 기대게 된 것은 사실이라 여기 적어 둔다.

### 하루 한 번은 "인기" 가 아니라 "그 순간" 이다 — 실측으로 확인했다

10:10 KST 는 **01:10 UTC** 다. 지역별로 이렇다.

```
01:10 UTC  =  한국·일본 아침 10시 · 유럽 새벽 3시 · 미국 동부 전날 저녁 9시
```

그래서 우리 숫자는 `이 게임을 몇 명이 하는가` 가 아니라 **`그 순간 접속해 있던
사람이 몇 명인가`** 다. 같은 날 01:00 과 07:30 UTC 에 재서 견줘 봤다.

| 게임 | 01:00 UTC | 07:30 UTC | |
|---|---:|---:|---:|
| PUBG: BATTLEGROUNDS | 102,136 | 320,864 | **+214%** |
| Apex Legends | 65,473 | 111,647 | +71% |
| Grand Theft Auto V | 38,891 | 48,171 | +24% |
| Counter-Strike 2 | 551,673 | 679,264 | +23% |
| HELLDIVERS 2 | 62,103 | 35,036 | **-44%** |
| Left 4 Dead 2 | 25,947 | 17,045 | -34% |

**방향이 게임마다 반대다.** 6시간 반 사이에 PUBG 는 세 배가 되고 HELLDIVERS 2 는
반토막이 났다. 전체가 같이 오르내린 것이 아니라 주 이용자 지역이 깨어났다 잠든
것이다. 그러니 **순위표는 인기 순위가 아니라 01:10 UTC 에 접속해 있던 사람의
순위**다.

#### 그래도 측정 시각은 바꾸지 않는다

**매일 같은 시각에 재야 어제와 오늘의 차이에 시각 차이가 안 섞인다.** 시각을
옮기거나 들쭉날쭉하게 재면 카드 5 의 변화값이 하루치 변화가 아니라 시간대 차이가
된다. 그리고 **중립적인 시각은 없다** — 어느 시각을 골라도 누군가는 자고 있다.

고칠 것은 재는 주기가 아니라 **화면이 하는 말**이다. 그래서 숨기는 대신 쟀다.

#### `data/timeprobe.json` 은 날짜별 기록과 완전히 별개다

| | `data/records.json` | `data/timeprobe.json` |
|---|---|---|
| 무엇 | 하루 한 건, 10:10 KST | 하루 중 아무 시각의 표본 |
| 열쇠 | 날짜 + appid, 중복 없음 | 잰 시각. 덧붙이기만 한다 |
| 카드 4·5 | **이것이 근거다** | **무관하다** |
| 만드는 것 | `scripts/collect.mjs` (Actions) | `scripts/probe-hours.mjs` (손으로) |

표본 파일은 **없어도 된다.** 못 읽으면 그 패널만 안 나오고 값·단위·날짜·비교는
하나도 안 바뀐다. 빌드도 이 파일이 없다고 실패하지 않는다. 재현 모드
(`?fault=`)에서는 아예 숨긴다 — 장애를 흉내내는 화면에 멀쩡히 받아온 보조 자료가
섞이면 무엇이 실패한 것인지 헷갈린다.

`probe-hours.mjs` 는 20분 안에 다시 돌리면 거절한다. 붙어 있는 표본 둘은 시각이
값을 흔드는 것을 못 보여주기 때문이다.

### DB 를 쓰지 않는다 — 안 써도 돼서가 아니라 쓰면 요건이 깨져서다

브리프가 요구하는 "지속되는 상태" 는 **카드 4** 하나다. `서로 다른 날짜의 값이
중복 없이 목록에 보인다` 이고, 통과 기준이 **"공개 주소에서 보인다"** 다.

| 저장 방식 | 카드 4 | 문제 |
|---|---|---|
| `localStorage` | **못 지킨다** | 심사자 브라우저에는 0건이다 |
| DB (Postgres 등) | 지킨다 | **접속 문자열 = 비밀값 1건** |
| **git 커밋 JSON** | 지킨다 | 없음 |

브리프의 조건에 `비밀값 0건 노출` 이 있다. DB 를 붙이는 순간 `DATABASE_URL` 이
생기고 **SECRET COUNT = 0 을 못 지킨다.** 지금 저장소에는 비밀값이 0건이다.

git 이 DB 보다 나은 지점이 셋 있다. 이 과제에 한해서다.

1. **감사 로그가 공짜다.** 기록 한 줄마다 커밋이 붙어 누가 언제 무엇을 넣었는지
   지울 수 없게 남는다. DB 라면 `audit_log` 를 따로 짜야 한다.
2. **심사자가 검증할 수 있다.** `git clone` 이면 끝이다. DB 면 접속 권한을 주거나
   (비밀값 노출) 확인을 못 하게 하거나 둘 중 하나다.
3. **값을 조용히 고칠 수 없다.** DB 는 `UPDATE` 한 줄로 어제 값을 바꿔도 흔적이
   안 남는다. `records.json 을 손으로 채우지 않는다` 는 규칙이 git 에서는 강제되고
   DB 에서는 신뢰에 맡겨진다.

#### DB 가 필요해지는 지점 — 파일 크기다

화면이 기록 파일을 **통째로** 받는다. 그래서 한계는 질의 성능이 아니라 파일 크기다.
실측(2026-08-27, 기록 건당 약 460 bytes) 기준이다.

| 기간 | 기록 수 | 파일 크기 |
|---|---:|---:|
| 하루 (75개) | 75 | 34 KB |
| 한 달 | 2,250 | 1.0 MB |
| **1년** | 27,375 | **12.0 MB** |
| 5년 | 136,875 | 60.1 MB |

**대략 한 달이 편안한 한계다.** 3~6개월이면 첫 화면이 눈에 띄게 느려진다.
이 과제는 기간이 2~3일이라 100 KB 언저리이고 문제 근처에도 가지 않는다.

#### 진짜 필요해지면 DB 가 첫 수순은 아니다

1. **날짜별로 파일을 쪼갠다** (`data/2026-08.json`). 화면은 필요한 달만 받는다.
   여전히 DB 가 없고 git 감사 로그도 그대로다.
2. **요약 파일을 따로 둔다.** 대표값만 담은 작은 파일을 첫 화면용으로.
3. **그다음에야 DB.** 여러 곳에서 동시에 쓰거나 임의 조건 검색이 필요할 때다.

지금은 쓰는 쪽이 **하루 한 번, 하나**다. DB 가 풀어 주는 문제(동시 쓰기, 대량 질의,
부분 읽기)가 셋 다 없다. 스프링을 안 쓴 것과 같은 논리다.

### 순위 이동 — 분모가 바뀐 것을 하락으로 만들지 않는다

[개선 명세](research/STEAM%20PULSE%20개선%20방향%20및%20가치%20고도화%20명세.md) 의 P1 중
실제로 비어 있던 것은 **순위 이동** 하나였다. 나머지(어제 대비 · 오른/내린 게임 ·
장르 리더 · 점유율 · 장애 5종 · 계산과 UI 분리)는 이미 서 있었다.

그냥 그날의 전체 순위끼리 견주면 안 된다. 재는 게임을 16개에서 75개로 늘린 다음
날, 어제 16개 중 3위였던 게임이 오늘 75개 중 20위가 된다. **이건 하락이 아니라
분모가 바뀐 것**인데 화면에는 하락으로 나온다. 값은 멀쩡한데 화면이 거짓말을 하는,
이 정보판이 잡아내려는 바로 그 종류다.

그래서 `rankMovement` 는 **양쪽 날에 다 있는 게임만으로 양쪽 순위를 다시 매긴다.**
그 개수를 화면이 적고, 빠진 것이 몇 개이며 왜 빠졌는지도 적는다 —
`새로 재기 시작했거나 어제 못 잰 것이지 순위에 들어온 것이 아니다`.

여기 순위가 줄세우기 패널의 순위와 다를 수 있다는 것도 화면에 적었다. **다른 것이
맞다.** 줄세우기는 오늘 잰 것 전부의 순위이고, 순위 이동은 견줄 수 있는 것만의
순위다.

### 개선 명세에서 안 가져온 것

| 제안 | 왜 안 가져왔나 |
|---|---|
| **`Top 75` 라는 표현** | 우리 75개는 **Steam 의 상위 75개가 아니다.** 장르 균형을 맞추려고 우리가 고른 75개이고 Portal(271명)·Antichamber(5명)가 들어 있다. 화면에 `Top 75` 라고 쓰면 명세 자신이 24절에서 금지한 종류의 거짓말이 된다 |
| **`NEW ENTRY`** | 우리 목록은 고정이라 **일어날 수 없다.** 명세의 판정식(`어제 없음 && 오늘 있음`)이 참이 되는 경우는 둘뿐이다 — 우리가 표에 넣었거나, 어제 못 쟀거나. 둘 다 "신규 진입" 이 아니다. 내일 새 59개가 전부 신규 진입으로 뜰 뻔했다 |
| `KING OF GENRE` 왕관 | 각 장르 1위는 이미 첫 줄에 보인다. 왕관은 순위 경쟁인 척만 더한다 |
| `Possible Context` (왜 올랐나) | Steam News · 할인 정보가 필요한데 전부 비공식 경로다. 인과를 만들어낼 위험도 크다 |
| `Comeback Radar` | 3년 이상 + 30% 상승 + 순위 5계단이 조건인데 이틀치로는 성립하지 않는다 |
| `Number Count` 애니메이션 | 숫자가 올라가는 연출은 신뢰를 다루는 화면에서 과장으로 읽힌다 |

`Top 75` 와 `NEW ENTRY` 둘은 **그대로 따랐으면 화면이 거짓말을 했을 것**이다.
명세가 좋은 문서인 것과 별개로, 우리 자료의 성질을 모르고 쓴 부분이 있었다.

### 대조 패널을 문서에서 화면으로 옮겼다

명세 34절의 `DATA PROOF` 다. 원자료 → 저장값 → 계산값 → 화면값이
[CROSSCHECK.md](CROSSCHECK.md) 에 이미 있었지만 **문서에만 있었다.** 검산하려면
저장소를 열어야 했다는 뜻이다. 접이식으로 화면에 두어 그 자리에서 확인되게 했다.

맨 위 줄이 제일 중요하다 — **원자료는 화면값과 일치하지 않는다.** 순간값이라
링크를 누를 때마다 다른 숫자가 나온다. 저장값 · 계산값 · 화면값 셋은 일치해야 하고
손계산 식이 그 자리에서 맞아야 한다.

내일 화면을 임시 2일치 파일로 미리 봤고 **곧바로 되돌렸다.** 지어낸 값은 커밋되지
않았다 (`git status` 로 확인). 확인한 것은 이렇다.

```
순위 이동   16줄 · PUBG ▲1 · Palworld ▼1 · 나머지 ─
손계산      570645 − 551673 = 18972
화면값      ▲ 18,972 명      ← 손계산과 같다
날짜 카드   27 오늘 · 28
```

`GitHub Actions` 로 바꾸자 통과했다. 공개 주소가 살아 있다.

**켜졌는지 판정하려면 API 가 아니라 배포를 돌려 봐야 한다.**

### 2. 멈춘 실행이 concurrency 그룹을 붙잡고 있었다

2026-08-26 수동 실행이 잡을 하나도 만들지 못한 채 `queued` 로 멈췄다.
`collect.yml` 이 `group: collect` 를 쓰므로 이후 예정 실행이 그 뒤에 줄을 선다.

**취소가 되지 않는다** — UI 가 `Failed to cancel workflow` 를 낸다. 잡이 배정된
적이 없어 붙잡을 프로세스가 없기 때문이다.

그래서 그룹 이름을 `collect-v2` 로 옮겨 빈 그룹을 쓰게 했다. 멈춘 실행이
취소되든 말든 상관없어진다. `cancel-in-progress` 도 `true` 로 바꿨다.

## 통화를 우리가 고르지 않는다 — 2026-08-28

공개 주소 `#/charts` 에 붉은사막이 `-20% ₩70 → ₩56` 으로 떠 있었다. 실제 한국
가격은 `₩79,800 → ₩63,840` 이다. **1000배 틀린 값이 공개 주소에 나가 있었다.**

저장값은 `initialMinor: 6999 / finalMinor: 5599` 였는데, 이건 원이 아니라 **USD
센트**다 — $69.99 → $55.99. Palworld $29.99, Dead by Daylight $19.99 로 미국
정가와 정확히 맞았다. 화면은 그것을 `/100` 하고 원화 기호를 붙이고 있었다.

### 원인 — `cc=KR` 은 무시된다

차트 URL 에 `cc=KR` 을 붙여 두었지만 이 파라미터는 통화를 바꾸지 않는다.
한국에서 세 나라 코드로 불러 확인했다.

```
cc=KR  →  ₩ 63,840
cc=US  →  ₩ 63,840     같다
cc=JP  →  ₩ 63,840     같다
```

통화를 정하는 것은 **호출한 IP** 다. 로컬(한국)에서 수집하면 KRW, Actions(미국
러너)에서 수집하면 USD 가 온다. 그래서 한 파일 안에 두 체계가 섞였다.

| 구역 | 실제 통화 | 화면 |
|---|---|---|
| `live.korea` · `live.global` · `weekly` · `monthly` | USD 센트 | ₩ (1000배 틀림) |
| `releaseCalendar.*` | KRW | ₩ (정상) |

출시 캘린더만 맞았던 이유는 그쪽이 화면 텍스트를 파싱했기 때문이다. 다만 그
`minorFromWon` 도 숫자 아닌 글자를 전부 지우고 100 을 곱하고 있어서, **미국
러너에서 도는 날 `$69.99` 를 ₩6,999 로 만들 자리였다.** 같은 결함이 잠복해 있었다.

### 고른 길 — 나눗셈을 없앤다

"어느 통화인지 알아내서 맞는 나눗셈을 고른다" 로 가지 않았다. 응답에 통화 코드
필드가 아예 없다. 있는 것은 `formatted_final_price` 하나이고, 그것이 **Steam
자신이 그 통화로 표기한 문자열**이다.

그래서 그것을 **그대로 옮겨 그대로 보여준다.** `finalMinor / 100` 을 지웠다.
우리가 단위를 고르지 않으면 단위를 틀릴 수도 없고, `화면값이 원자료와 일치한다`
가 계산 없이 성립한다.

`initialMinor`·`finalMinor` 는 보존하되 **그 숫자의 단위는 `currency` 이지 항상
원이 아니다.** 그리고 `currency` 는 확신할 때만 채운다 — `₩` 는 `KRW` 로 읽고,
`$` 는 `null` 로 둔다. `$` 를 USD 로 단정하는 것은 방금 고친 결함을 형태만 바꿔
되풀이하는 일이다. 이 값의 쓰임은 "한국 가격이라고 불러도 되는가" 하나뿐이고,
거기에는 KRW 인지 아닌지만 있으면 된다.

### 화면이 스스로 밝힌다

- `한국 가격` 이라고 부르지 않는다. 통화가 수집 위치에 달렸기 때문이다
- 지금 떠 있는 표기(`₩`)를 화면이 센다. 섞이면 `$ · ₩` 처럼 섞였다고 적는다
- **순위는 통화와 무관하다** — 한국 차트 주소에서 오므로. 그 구분도 적었다

### 가드를 안 단 자리였다

성인 분류에는 `assertDescriptorsPresent` 를 달아 두고 통화에는 안 달았다.
`assertPriceTextPresent` 를 세 구역에 달았다 — 가격이 붙은 항목이 있는데 표기를
한 건도 못 읽으면 응답 형식이 바뀐 것으로 보고 기존 스냅샷을 덮지 않는다.

**교훈은 가드의 위치다.** 한 곳에 스키마 가드를 달 이유가 있었다면, 같은 응답에서
읽는 다른 필드에도 대개 같은 이유가 있다.

## 빌드 설정 안의 판단을 테스트가 보는 자리로 내린다 — 2026-08-29

`npm run dev` 가 백지였다. `serve-data` 미들웨어가 `/data/*.json` 으로 **시작하는**
요청을 전부 원문 JSON 으로 내주고 있었고, `OverviewStrip` 이 같은 파일을 ESM 으로
들여오면서 Vite 가 부르는 `?import` 주소까지 가로챘다. 자세한 경위는
[DEFECTS 17번](DEFECTS.md).

1. **목록과 경로 판단은 `src/source/dataFiles.js` 에 둔다.** `vite.config.js` 는
   `matchDataFile()` 을 부르기만 한다. `test/dataFiles.test.js` 가 화면이 fetch 하는
   주소·`?import`·앞부분만 같은 주소를 각각 본다.
2. **질의가 붙은 요청은 미들웨어가 비켜선다.** 같은 파일이라도 fetch 와 ESM import 는
   서로 다른 응답을 원한다. 하나로 처리하면 둘 중 하나가 틀린 것을 받는다.
3. **`ui` 에 계산을 두지 않는 규칙은 빌드 설정에도 적용된다.** 브라우저를 띄워야만
   보이는 자리에 판단을 두지 않는다.
4. **검증 경로를 하나만 쓰지 않는다.** 어제 웹디자인 여덟 커밋은 `build` + `preview`
   로만 확인했고, 그래서 `dev` 가 죽은 것을 하루 반 동안 아무도 몰랐다. 화면을
   만졌으면 **띄우는 방법 둘 다** 한 번씩 지나간다.

## 한 날짜 안의 시각 차이 — 값은 두고 화면이 밝힌다 — 2026-08-29

하루가 한 번에 잰 것이라는 보장이 없다. `pendingGamesForDate` 는 그날 빠진 게임만
채우므로 목록이 늘거나 일부가 실패한 날은 한 날짜가 두 배치가 된다. 2026-08-27 이
그랬다 — 16개는 09:59 KST, 59개는 20:09 KST 로 **10시간 10분** 차다.

`movers` 만 5분 배치 창을 쓰고 `leaderboard`·`byGenre`·`graveyard`·`rankMovement`
는 날짜로만 골랐다. 그래서 순위 이동 패널이 어제 저녁 값과 오늘 아침 값을 59개
견주면서 화면에는 시각을 한마디도 안 적고 있었다.

1. **값을 빼지 않는다.** 다른 시각에 잰 줄도 실제로 잰 값이다. 빼면 그날 잰 것을
   우리가 화면에서 지우는 쪽이 된다. 오래된 값을 지우지 않고 오래됐다고 적은 것,
   접은 항목의 순위를 지우지 않고 접었다고 적은 것과 같은 자리다.
2. **비교만 예외다.** `movers` 는 그대로 배치 창을 쓴다. 차이를 **만드는** 계산이라
   시각이 다르면 없는 변화를 만들어 내기 때문이다. 줄세우기·합계·순위는 값을
   나열할 뿐이라 다르다. 이 구분을 `measurementSpread` 주석에 적었다.
3. **화면이 언제 잰 것인지 말한다.** 구간·길이·대표 배치에서 벗어난 개수를 적고,
   벗어난 줄에만 그 줄의 시각을 단다. 전부 달면 같은 배치인 날에도 잡음이 된다.
4. **한 배치로 잰 날은 아무 말도 하지 않는다.** 없는 경고를 만들지 않는다.
   2026-08-28 은 20초 안에 다 쟀으므로 그 세 패널은 조용하다.
5. **문장은 `SpreadNote` 한 곳에 둔다.** 네 패널이 같은 사실을 말하므로 네 곳에
   적으면 갈라진다. `subject` 는 **조사까지 붙여서** 받는다 — 여기서 은/는을
   붙였더니 `이 순위은` 이 나왔다.

배치 기준은 대표 게임을 잰 시각이고 `App` 이 네 패널에 같은 `anchorAppid` 를
넘긴다. 한 화면 안에서 `대표 배치` 가 패널마다 다른 것을 가리키면 안 된다.
