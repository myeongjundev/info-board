# GAME PULSE 프론트 2차 설계

작성일: 2026-08-29  
작업 브랜치: `codex/frontend-redesign`  
목표: Steam 카운터처럼 보이는 화면을 **출처가 분명한 게임 시장 인텔리전스 제품**으로 정리한다.

## 1. 이번 개편이 답해야 하는 것

처음 온 사용자가 15초 안에 아래 네 질문에 답할 수 있어야 한다.

1. 지금 무엇을 많이 플레이하는가?
2. 지금 무엇이 많이 팔리는가?
3. 지금 무엇이 할인·무료인가?
4. 지금 무엇을 많이 시청하는가?

그 다음 행동은 둘 중 하나다.

- 게임 하나를 골라 상세 근거를 본다.
- 순위의 출처·조회 시각·한계를 확인한다.

따라서 첫 화면은 `요약 → 게임 선택 → 근거 확인` 순서로 설계한다. 기능을 늘리는 것이
아니라 이미 있는 자료의 탐색 순서를 바로잡는 작업이다.

## 2. 벤치마킹을 어디에 쓸지

| 참고 | 가져올 장점 | GAME PULSE 적용 위치 | 가져오지 않을 것 |
|---|---|---|---|
| Steam 공식 Charts | 현재·주간·월간의 명확한 구분, 지역 전환 | 매출 순위 | 판매량·매출액처럼 Steam이 공개하지 않는 값 |
| SteamDB | 고밀도 순위표, 숫자 열 정렬, 작은 변화 표시 | 동시접속·매출·할인 목록 | 실시간처럼 보이는 표현, 보유하지 않은 장기 이력 |
| VG Insights | 큰 KPI와 게임 단위 Quick Stats | 첫 화면, 게임 상세 패널 | 추정 매출·판매량·소유자 수 |
| TwitchTracker | 현재값과 기간·변화의 구분 | 스트리밍 순위 | 기록이 쌓이기 전 7일·30일 추이 |
| SullyGnome | 수집 주기와 표본 한계의 명시 | 데이터 품질 | 플랫폼 간 시청자 합산 순위 |

원칙은 하나다. **형태는 벤치마킹하되 값은 현재 저장 파일에 있는 것만 쓴다.**

## 3. 전체 정보구조

```text
공통 상단
├─ 브랜드와 서비스 설명
├─ 게임 통합 검색
├─ 네 축 전환
└─ 자료 상태·최근 조회 시각

첫 화면
├─ 시장 요약: 네 축 대표값
├─ Steam 동시접속 Quick Stats
├─ 최근 측정 이력
├─ 데이터 품질: 출처·대조·장애
└─ 인사이트: 시각·장르·순위·변화·장기 생존

매출 순위
├─ 지역 전환: 한국 / 글로벌
├─ 현재 매출 Top 20
├─ 주간 Top 20과 순위 변화
├─ 신작 출시 캘린더
└─ 자료 정의와 통화 한계

할인·무료
├─ Epic 기간 한정 무료
├─ Steam 무료 소장 / 무료 주말
├─ 인기 100 표본 할인
├─ 추적 75개 할인
└─ 출처와 비공식 경로 고지

시청 순위
├─ 플랫폼 상태
├─ 치지직 / Twitch 전환
├─ 현재 Top 10과 직전 정상 표본 변화
├─ 두 차트 공통 게임
└─ 수집 방식과 표본 한계
```

## 4. 공통 화면 골격

### 4-1. App Shell

- 데스크톱: 브랜드 / 검색 / 네 축 / 상태를 한 줄에 둔다.
- 태블릿: 브랜드와 네 축, 검색을 다음 줄에 둔다.
- 모바일: 브랜드 → 네 축 가로 탐색 → 검색 순서로 세 줄을 유지한다.
- 활성 페이지는 색만 바꾸지 않고 얇은 하단선과 `aria-current`를 함께 쓴다.
- `LIVE`를 사용하지 않는다. `최근 10:39 측정`처럼 실제 조회 시각을 쓴다.

### 4-2. Page Header

모든 페이지의 첫 구역을 같은 문법으로 통일한다.

```text
[영문 분류 라벨]                 [자료 상태 / 조회 시각]
페이지가 답하는 질문
한 문장 설명
[대표 KPI 1] [대표 KPI 2] [대표 KPI 3]
```

질문형 문구는 페이지 제목에만 사용하고, 나브는 `동시접속 · 매출 순위 · 할인·무료 ·
시청 순위`처럼 짧은 명사로 유지한다.

### 4-3. Rank Table

SteamDB의 밀도를 참고하되 다음 열만 허용한다.

```text
순위 | 게임 | 현재값 | 변화 | 보조값 | 행동
```

- 숫자는 오른쪽 정렬하고 고정폭 숫자를 사용한다.
- 게임 이미지가 실패해도 숫자 열은 움직이지 않는다.
- 성인 분류로 접힌 항목은 기존 규칙대로 자리만 지킨다.
- 긴 목록은 12행을 기본으로 보여주고 `전체 보기 / 목록 접기`를 제공한다.
- 모바일에서는 이미지·부가 설명을 줄이되 순위·이름·핵심값은 남긴다.
- 표 헤더는 목록이 12행을 넘는 화면에서만 고정한다.

### 4-4. Data Quality Block

데이터 품질은 별도 페이지로 숨기지 않는다. 해당 숫자와 같은 페이지 아래에 둔다.

- 출처
- 원천 관측 시각과 조회 시각
- 수집 주기
- 표본 범위
- 실패 시 표현
- 공식 자료와 비공식 수집 경로의 구분

접을 수 있는 상세 설명은 허용하지만, 출처 이름·자료 상태·조회 시각은 접지 않는다.

## 5. 첫 화면 상세 설계

### 5-1. Market Overview

현재 구현한 네 축 보드를 유지한다. 각 카드는 다음 구조를 공유한다.

```text
축 이름 / 번호
대표 숫자
대표 게임 또는 행사
자료 상태 한 줄
상세 보기 →
```

첫 화면 1280×720에서 상단 나브와 네 축 카드 네 개가 모두 보여야 한다. 네 축 아래의
Steam 상세는 일부만 보여도 되지만, 다음 구역이 있다는 것은 보여야 한다.

### 5-2. Steam Quick Stats

VG Insights의 Quick Stats 문법을 적용한다.

- 대표 게임 현재 접속자
- 이전 측정 대비
- 실제 조회 시각
- 측정 성공 범위

네 카드는 모두 같은 크기로 만들지 않는다. 대표값은 2칸, 나머지는 1칸으로 두되 값과
단위가 줄바꿈되지 않는 최소 폭을 지킨다.

### 5-3. Game Focus Panel

검색이나 순위에서 게임을 선택하면 별도 모달보다 페이지 안의 상세 패널을 우선한다.

```text
[표지] 게임명 · 출시연도
현재 동시접속 | 전일 변화 | 측정 순위 | 장르
최근 기록 미니 추이
[Steam 상점] [가격 보기] [원자료]
```

1차 구현은 `records.json`과 코드 게임 표에 있는 정보만 쓴다. 매출·할인·스트리밍과의
연결은 appid 또는 검토된 별칭이 확실한 경우에만 추가한다. 이름이 비슷하다는 이유로
자동 결합하지 않는다.

## 6. 페이지별 설계

### 6-1. 매출 순위

- 가장 위에 `한국 / 글로벌` 세그먼트 컨트롤을 둔다.
- 선택 지역의 현재 Top 20을 첫 표로 둔다.
- 주간 순위는 별도 표로 두고 `▲ · ▼ · 신규 · 연속 주차`를 한 열에 정돈한다.
- 현재와 주간을 탭으로 숨기지 않는다. 같은 페이지에서 순서대로 확인할 수 있어야 한다.
- 월간 인기 신작은 순위가 없는 목록이므로 숫자 순위처럼 꾸미지 않는다.
- 통화는 저장된 `currency`와 원문 가격만 표시한다.

### 6-2. 할인·무료

첫 화면을 행사 유형별 탭이 아니라 **상태별 요약 + 구역 이동**으로 만든다.

```text
무료 소장 n | 무료 주말 n | Epic 무료 n | 할인 중 n
```

- 종료가 있는 무료 행사는 남은 시간을 가장 먼저 보여준다.
- 가격·할인율·상점 링크는 한 카드 안에서 찾을 수 있게 한다.
- 인기 100 표본과 추적 75개는 하나의 목록처럼 합치지 않는다.
- 중복 게임 수는 요약 계산에서 appid 합집합을 사용한 현재 계약을 유지한다.

### 6-3. 시청 순위

- 플랫폼 상태를 먼저 보여주고 정상인 플랫폼만 순위 전환을 허용한다.
- 기간 선택처럼 보이는 UI는 만들지 않는다. 현재 보유한 것은 `현재 / 직전 정상 표본`이다.
- 순위 변화와 시청자 변화를 한 줄에 함께 표시한다.
- 치지직과 Twitch 시청자를 더한 통합 점수는 만들지 않는다.
- 공통 게임 카드는 두 플랫폼의 순위와 값을 나란히 보여주는 대조 카드로 유지한다.

## 7. 공통 컴포넌트 후보

새 의존성을 추가하지 않고 현재 React와 CSS로 만든다.

| 컴포넌트 | 역할 |
|---|---|
| `PageHero` | 분류 라벨·제목·설명·조회 상태 |
| `MetricCard` | 값·단위·보조 설명·상태 |
| `SegmentControl` | 한국/글로벌, 치지직/Twitch 전환 |
| `RankTable` | 순위 열 정렬과 모바일 축약 |
| `ListDisclosure` | 12행/전체 목록 전환 |
| `DataQualityBlock` | 출처·시각·제약의 공통 틀 |
| `GameFocusPanel` | 선택 게임의 Quick Stats |

처음부터 전부 추상화하지 않는다. 두 화면에서 같은 형태가 확인된 뒤 공통 컴포넌트로
올린다. 한 화면만 쓰는 컴포넌트를 공통 폴더로 옮기지 않는다.

## 8. 구현 순서

### Phase 0 — 병합 기준점

1. Claude의 결함 수정이 main에 들어간다.
2. `codex/frontend-redesign`을 최신 main 위로 재배치한다.
3. 충돌이 나면 데이터·수집기·상태 모델은 main을 우선하고 UI 변경만 다시 적용한다.

### Phase 1 — 공통 기반

1. 디자인 토큰을 파일 끝 덮어쓰기에서 의미별 구역으로 정리한다.
2. `PageHero`, `SegmentControl`, `ListDisclosure`를 만든다.
3. 공통 포커스·빈 상태·오류 상태를 정렬한다.

### Phase 2 — 첫 화면

1. Market Overview와 Steam Quick Stats를 한 리듬으로 맞춘다.
2. `GameFocusPanel`을 추가한다.
3. 데이터 품질의 첫 줄에 출처·조회 시각·상태를 고정한다.

### Phase 3 — 매출 순위

1. 현재·주간 표의 열 구조를 통일한다.
2. 지역 전환을 공통 세그먼트로 교체한다.
3. 출시 캘린더와 월간 신작의 시각적 역할을 분리한다.

### Phase 4 — 할인·무료

1. 네 상태 요약을 추가한다.
2. 무료 행사 카드는 종료 시각 중심으로 재정렬한다.
3. 인기 표본과 고정 추적 목록의 모집단 차이를 제목에서 바로 보이게 한다.

### Phase 5 — 스트리밍

1. 플랫폼 카드와 전환 컨트롤을 합친다.
2. 순위·시청자 변화 열을 정돈한다.
3. 공통 게임 대조 카드와 데이터 품질을 같은 시각 언어로 맞춘다.

### Phase 6 — 검증

1. 1280×720, 1440×900, 375×812에서 시각 검증한다.
2. 키보드만으로 검색·전환·전체 보기·상점 링크에 접근한다.
3. 정상·오래됨·빈 값·장애 5종·fixture 회복을 확인한다.
4. `npm test`, `npm run audit:t04`, `npm run build`를 실행한다.

## 9. 완료 기준

| 항목 | 통과 기준 |
|---|---|
| 첫인상 | 첫 720px 안에 브랜드, 네 축, 네 대표값, 자료 날짜가 보임 |
| 탐색 | 어느 페이지에서도 다른 세 축으로 두 번 이내 이동 |
| 긴 목록 | 기본 12행, 전체 보기와 접기 제공, 데이터 자체는 삭제하지 않음 |
| 모바일 | 360px 이상에서 문서 가로 스크롤 0 |
| 숫자 | 값·단위·순위·변화가 줄바꿈 때문에 분리되지 않음 |
| 신뢰 | 출처·조회 시각·자료 상태가 같은 페이지에 표시됨 |
| 상태 | 실패를 0이나 빈 정상 목록으로 표현하지 않음 |
| 접근성 | 활성 전환 `aria-current/selected`, 펼침 `aria-expanded`, 포커스 표시 |
| 회귀 | 243개 이상 테스트 통과, T04 FAIL 0, 프로덕션 빌드 성공 |

## 10. Claude 작업과의 경계

Codex가 다루는 파일:

- `src/ui/*.jsx`
- `src/ui/styles.css`
- 필요할 때 UI 전용 표현 계산 테스트

Claude가 결함 수정 중인 영역은 병합 전까지 건드리지 않는다.

- `src/state/**`
- `src/source/**`
- `scripts/**`
- `data/**`
- `vite.config.js`

UI가 새 값을 요구하는 순간 임의 계산을 넣지 않는다. 필요한 데이터 계약을 한 줄로
정의해 Claude에게 넘기고, 계약이 main에 들어온 다음 화면을 연결한다.

## 11. 바로 다음 작업

Phase 0 이후 **Phase 1과 Phase 2를 한 묶음**으로 진행한다. 첫 화면과 공통 기반을 먼저
완료하면 나머지 세 페이지는 같은 컴포넌트 문법으로 반복 적용할 수 있다. 첫 검토 지점은
1280×720 첫 화면과 375×812 모바일 첫 화면 두 장이다.
